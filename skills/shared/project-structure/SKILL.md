# Архитектура хранения проектов

Правило общее для всех агентов: Claude Code, Antigravity, Cowork, локальные агенты.

## Главный принцип: папка проекта самодостаточна

Всё, что нужно агенту для работы над проектом, лежит внутри папки проекта.
Папку можно открыть в любой агентной системе — новый аккаунт Claude,
Antigravity, локальная модель на Ollama — и она заработает без донастройки.

Следствия, которые нарушать нельзя:

- Никаких абсолютных путей за пределы папки. Внутри — только относительные.
  Исключение — данные, которые намеренно живут на другом томе; тогда путь
  задаётся одной константой и это записано в `CLAUDE.md` проекта.
- Никаких реальных секретов в git. Только `.env.example` с именами переменных;
  сам `.env` закрыт `.gitignore`.
- Общий скилл, который нужен этому проекту постоянно, копируется внутрь
  проекта, а не подключается ссылкой из профиля пользователя.

`.venv`, `.git`, `node_modules` внутри проекта — нормально: хранилище
локальное, облачной синхронизации нет.

## Корни

```
AI Projects/           Mac: ~/Desktop/AI Projects   Windows: C:\AI Projects
├── _instruments/      общая библиотека: skills, agents, docs, templates, scripts
├── Claude/            проекты, которые ведёт Claude
├── Antigravity/       проекты, которые ведёт Antigravity
└── Local/             закрытые проекты: только локальная модель, без облака
```

Раскладка одинаковая на обеих машинах; `_instruments` — git-репозиторий
`instruments` (только рабочие скиллы и правила), синхронизация Mac ↔ Windows —
автосинхронизация (README `_instruments`). Работа над скиллами — в мастерской
`Claude/ai-workshop`, репозиторий `ai-workshop`.
Всё на локальном диске (Windows — NTFS, Mac — APFS). Google Диск больше
не используется: он не NTFS, на нём не работают junction-ссылки и нет
исключений по маске.

## Структура проекта

```
<project-name>\
├── CLAUDE.md          единственный вход в контекст: коротко + карта справочников
├── AGENTS.md          стаб: ведёт в CLAUDE.md, называет папку скиллов
├── GUARDRAILS.md      ограничения, включая «работать только внутри папки»
├── STATE.md           живая страница смены (если проект ведут два агента)
├── .env.example       имена переменных окружения, без значений
├── .claude\skills\    скиллы проекта: <имя>\SKILL.md
├── docs\              решения, исследования, спеки
│   └── context\       справочники по линиям проекта (когда CLAUDE.md разросся)
├── agents\            роли и промпты
├── mcp\               конфиги MCP-серверов
├── scripts\           утилиты
├── src\               исходники
├── data\              входные и рабочие данные, вне git
└── out\               финальные результаты
```

Шаблон: `_instruments/templates/project/`.
Новый проект — скилл `new-project`: Mac — `new-project.command` в корне
AI Projects (или `_instruments/scripts/new-project.sh`), Windows —
`new-project.bat <Claude|Antigravity> <имя>`. Ненужные папки из шаблона удалять.

Папка скиллов проекта ровно одна — `.claude\skills\`. Она названа так потому,
что это единственное место, которое агент подхватывает из папки проекта сам.
Остальным агентам путь называет `AGENTS.md`. Второй папки `skills\` рядом
не заводить — это источник расхождений.

## Один вход в контекст

Вход ровно один — `CLAUDE.md`. `AGENTS.md` и `.antigravity\GEMINI.md` —
стабы со ссылкой на него. Второго входа рядом не заводить (`CONTEXT.md`,
`README` для агента и т. п.).

`CLAUDE.md` грузится сам в каждую сессию — и в каждого сабагента, и в каждый
запуск `claude -p` по таймеру. Поэтому в нём только то, что нужно в любой
сессии: начало смены, о проекте в двух абзацах, ключевые решения, рабочие
правила, где что лежит. Ориентир — до ~10–12 КБ.

Разросся (несколько линий: сайт, сервер, контент…) — подробности по линиям
выносятся в справочники `docs\context\<линия>.md`, а в `CLAUDE.md` остаётся
карта:

```markdown
| Задача про… | Читать |
|---|---|
| сервер, службы | `docs\context\server.md` |
```

Правила справочников:

- Ссылка — простым путём. **Не `@файл`**: импорт через `@` грузит файл в
  каждую сессию целиком, и деление теряет смысл.
- Справочник открывают только под задачу; каждый факт живёт в одном месте
  (в справочнике — не повторять `CLAUDE.md`, и наоборот).
- Новое знание о линии — в её справочник; в `CLAUDE.md` — только нужное всем.
- Это живые файлы: без даты в имени. Подробные разборы и планы — как раньше,
  `docs\ГГГГ-ММ-ДД_*.md`, справочник на них ссылается.
- Агентам по расписанию (рутинам) — свой текст с явным списком, что читать;
  `CLAUDE.md` они получают и так, перечитывать его не просить.

`STATE.md` — тоже коротко (сейчас / дальше / открытые вопросы); законченное
уходит в журнал решений или архив `docs\state-archive\`.

## Именование

- Папки проектов и скиллов: латиница, kebab-case, без пробелов.
- Документы: `ГГГГ-ММ-ДД_название-латиницей.md`; `_vN` только для новой редакции.
- Живые файлы (`CLAUDE.md`, `STATE.md`, `GUARDRAILS.md`, `docs\context\*.md`) даты в имени не несут.
- Имя папки скилла обязано совпадать с полем `name:` во фронтматтере.

## Скиллы: что где

Формат одинаков у Claude и Antigravity: `<имя-скилла>\SKILL.md`, фронтматтер
с `name` и `description`. Вложенность ровно один уровень — папка с двумя
уровнями не загрузится ни у кого.

Библиотека делится по применимости:

```
_instruments\skills\
├── shared\        работают у обоих агентов
├── claude\        только Claude Code / Cowork
└── antigravity\   только Antigravity
```

- Нужно одному проекту — `<project>\.claude\skills\`. Едет вместе с папкой.
- Переносимое знание, нужное везде — `_instruments/skills/shared/`,
  раздаётся ссылками в профиль пользователя установщиком: Mac — `zsh install.sh`
  (символические ссылки в `~/.claude/skills/`, `~/.gemini/config/skills/` — Antigravity IDE,
  `~/.gemini/antigravity-cli/skills/` — CLI `agy`),
  Windows — `install.ps1` (junction-ссылки, как ниже). Руками на Windows:

```cmd
mklink /J "C:\Users\<user>\.claude\skills\<имя>"        "C:\AI Projects\_instruments\skills\shared\<имя>"
mklink /J "C:\Users\<user>\.gemini\config\skills\<имя>" "C:\AI Projects\_instruments\skills\shared\<имя>"
```

- Инструкции про инструменты конкретного агента (Desktop Commander, device_bash,
  тулзы Antigravity) в `shared\` НЕ класть: чужой агент прочитает и начнёт
  звать несуществующие инструменты. Им место в `claude\` или `antigravity\`.

Junction (Windows) и символическая ссылка (Mac) — не копия и не ярлык,
а запись «эта папка на самом деле вон там». Junction создаётся только на
локальном NTFS; `rmdir` без `/S` снимает ссылку, не трогая цель. На маке
ссылку снимает `rm <ссылка>` (без `-r`), цель остаётся.

## Как подключить папку проекта к агенту

- Claude Code или новый аккаунт Claude: открыть папку как рабочую директорию.
  `CLAUDE.md` и `.claude\skills\` подхватятся сами.
- Antigravity: открыть папку как workspace, точка входа — `AGENTS.md`.
- Локальный агент (Ollama и подобные): `CLAUDE.md` как системный контекст,
  `.claude\skills\*\SKILL.md` как дополнительные инструкции.

## Работа двумя агентами

Деление `Claude\` / `Antigravity\` означает, **кто ведёт проект**, а не кто
единственный имеет к нему доступ. Один проект — одна папка; второй агент
открывает ту же папку. Второго клона и второго рабочего дерева не заводить:
работа идёт поочерёдно, коллизий нет.

В таких проектах появляется `STATE.md` в корне — живая страница смены.
Правила деления задач и приёмки — скилл `agent-workflow`.

## Закрытые проекты (Local)

Третий вид проектов — **закрытые**: их ведёт только локальная модель
(Ollama + Open WebUI на этом ПК). Данные не попадают в облачные агенты.

Корень: `C:\AI Projects\Local\<проект>\`, структура та же, что у остальных
проектов (шаблон `_instruments/templates/project` + оверлей `project-local`).

Как работает закрытый проект:

- **Агент** — Open WebUI (http://127.0.0.1:3000) с локальной моделью.
  Для каждого проекта есть пресет модели с id `local-<имя-папки>`;
  его системный промпт = `CLAUDE.md` проекта. Создаёт пресет `new-project`
  (если Open WebUI запущен), обновляет - `sync-webui.bat` в корне проекта
  (обёртка над `local-gpt\scripts\sync_webui_project.py`).
- **Инструмент `project_files`** (функции `list_files`, `read_file`,
  `write_file`, `update_section`, `save_summary`) читает и пишет файлы только внутри
  папки проекта. Перезапись — с копией в `data/.versions/`. `update_section` меняет
  один раздел по заголовку, остальное не трогает; `save_summary` сам составляет имя
  итога по шаблону. Правка `CLAUDE.md`, `GUARDRAILS.md`, `docs/context/` сама обновляет пресет.
  Команды: `/итог` — итог в `docs/` и `STATE.md`; `/контекст` — новые факты по местам. В именах файлов закрытого проекта — только нейтральные слова:
  имена видны снаружи (списки, логи, линтер).
- **База знаний пресета** — `GUARDRAILS.md` и `docs/context/*.md`; `STATE.md` в неё
  не кладётся: модель меняет его сама и читает с диска.
- **Передача смены**: команда `/итог` → записка в
  `docs/ГГГГ-ММ-ДД_itog-<тема-латиницей>.md` + главное в `STATE.md`.
- **Чаты** живут в базе Open WebUI (`local-gpt/data/open-webui/`),
  не в папке проекта: всё ценное — через `/итог` в md.
- **Git** — только локальный, без удалённого репозитория (или без git).
  Бэкап — копия папки на диск J: или L:.
- **Mac**: моделей нет, ветку Local создать можно, но работать в ней нечем.

`CLAUDE.md` и `GUARDRAILS.md` в Local-проектах начинаются с маркера
`> ЗАКРЫТЫЙ ПРОЕКТ: только локальные модели.` — облачным агентам
содержимое не читать и не менять.

## Запреты

- Не коммитить секреты: `.env`, токены, ключи, `secrets.json`.
- Не собирать скиллы из проектов в библиотеку автоматически: направление
  только сверху вниз, библиотека — источник.
- Не оставлять в коде абсолютные пути наружу. Скрипт должен находить себя
  сам: `_HERE = os.path.dirname(os.path.abspath(__file__))`.
- Не заводить второй вход в контекст рядом с `CLAUDE.md`; справочники —
  только в `docs\context\` и только по карте из `CLAUDE.md`.
- Не хранить данные пользователей в git: профили, письма, базы — в `data\`,
  закрытой `.gitignore`.

## Проверка соответствия

Стандарт — это то, чем меряют, а не то, что применяют автоматически.
`CLAUDE.md`, `GUARDRAILS.md`, `STATE.md` в каждом проекте содержат живой
текст; массовое приведение к шаблону затёрло бы его.

Поэтому есть линтер, который **ничего не меняет**:

```bash
# Mac
python3 -X utf8 ~/Desktop/"AI Projects"/_instruments/scripts/check-structure.py
```

```cmd
:: Windows
python -X utf8 "C:\AI Projects\_instruments\scripts\check-structure.py"
```

Он проверяет имена папок, обязательные файлы, отсутствие второй папки
скиллов, глубину вложенности скиллов, закрыты ли секреты `.gitignore`,
следы старой архитектуры (Google Диск, том `K:`) и показывает абсолютные
пути наружу (`C:\...` и `/Users/...` вне AI Projects). Отчёт пишется рядом в `check-structure.log`.
Что чинить — решает человек.

Историю переезда линтер не считает ошибкой: документы, которые описывают
прошлое, перечислены в списке `HISTORICAL` внутри скрипта. Новый такой
документ туда добавляется руками.

Запускать после каждого изменения стандарта. Задача исполнительская,
критерий однозначный — подходит для делегирования.

## Как изменения доходят до агентов

- **Скилл в библиотеке** → Claude Code и Antigravity читают новую версию сами,
  через junction / симлинк, со следующего запуска. Новый скилл — запустить
  установщик (`install.sh` / `install.ps1`), иначе ссылки на него не будет.
- **Аккаунтная копия в Cowork** → только вручную, карточкой скилла.
- **Шаблон проекта** → влияет только на новые проекты, старые не трогает.
- **Существующие проекты** → сами не меняются и не должны. Хочешь применить
  изменение — прогнать линтер, посмотреть расхождения, починить точечно.

Правило про две копии скилла: **правка файла в библиотеке и карточка идут
в одном ходе.** Если карточку не отправили — сказать прямо, чтобы расхождение
было видно. Молча оставлять аккаунтную копию позади нельзя: Cowork будет
работать по устаревшему правилу, и это проявится только неверными решениями.
